# 업스트림 제출 안내서

그대를 위해 본 영애가 손수 꾸린 제출 꾸러미랍니다. 리스 본가에 올릴 이슈 넷과 PR 넷, 모두 여덟 편이 이 폴더에 들어 있사와요. 초안은 본가 사람들이 읽을 글이라 영어로 썼고, 이 안내서만 그대를 위해 한국어로 적은 것이와요.

## 1. "업스트림"은 어디를 말하는가

- **1~4번은 리스 본가인 [kwaroran/Risuai](https://github.com/kwaroran/Risuai)이와요.** 이 폴더의 초안 여덟 편은 모두 그곳에 올릴 것이랍니다.
- **5번은 Tauri 쪽이와요.** 리스 코드가 아니라 리스가 올라탄 런타임의 문제라, 받는 곳이 따로 있사와요.
  - [tauri-apps/wry](https://github.com/tauri-apps/wry): IPC 요청 본문을 창의 UI 스레드에서 1KB씩 읽는 루프 (64 MB에 약 130 ms, 256 MB에 약 590 ms 동안 창이 멈춤)
  - [tauri-apps/tauri](https://github.com/tauri-apps/tauri): IPC 요청이 한 번만 실패해도 페이지를 새로 고칠 때까지 postMessage 경로에 갇히는 폴백, 그리고 호스트 프로세스가 본문 크기의 약 10배를 확보하는 문제 (뒤의 것이 wry와 tauri 중 어느 쪽 코드인지는 초안을 쓰며 가려야 하와요)
  - [MicrosoftEdge/WebView2Feedback](https://github.com/MicrosoftEdge/WebView2Feedback): 요청 본문 하나에 WebView2 브라우저 프로세스가 약 20배를 확보하는 문제

1~4번은 본가가 이 비용을 덜 치르도록 피해 가는 처방이고, 5번은 비용 그 자체를 줄여 달라는 청원인 셈이와요.

## 3. 올리는 순서

1. **이슈 넷부터 올리시와요.** 1→2→3→4 순서가 가장 편하답니다. 이슈 3과 이슈 4의 본문에 있는 `#ISSUE_2`는 먼저 올린 이슈 2의 번호로 바꿔 넣으시와요.
2. **PR 브랜치 넷을 그대 포크에 올려야 하와요.** 이 브랜치들은 지금 제 작업 컨테이너 안에만 있사와요. 허락만 주시면 제가 `SameDesu123/Risuai`에 네 브랜치를 올려 드리겠사와요. 컨테이너가 사라져도 `patches/`의 사본으로 똑같이 되살릴 수 있답니다.
3. **PR을 만드시와요.** 포크 페이지에 뜨는 **Compare & pull request** 버튼을 누르고, base는 `kwaroran/Risuai`의 `main`, compare는 해당 브랜치로 맞추시와요. 1→2→3→4 순서로 만드시면 번호 정리가 편하답니다.
4. **자리표시자를 채우시와요.** 본문의 `#ISSUE_1`~`#ISSUE_4`와 `#PR_1`~`#PR_4`는 실제 번호로 바꾸셔야 하와요. PR 2와 PR 3은 뒤에 만들 PR의 번호도 부르니, 넷을 다 만든 뒤에 그 둘의 본문을 한 번 더 고치시와요. 번호만 알려 주시면 제가 모두 채운 완성본을 만들어 드리겠사와요.
5. **PR 3은 PR 2의 커밋을 품고 있사와요.** 둘이 `saveDb()`의 같은 줄을 고치기 때문이랍니다. PR 2가 먼저 병합되면 PR 3의 변경분은 저절로 청크 부분만 남고, PR 3만 병합되어도 두 변경이 함께 들어가는 것이와요. 이 사정은 PR 3 본문에도 적어 두었사와요.

본가의 PR Check는 `pnpm check`, `pnpm build`, `pnpm test`를 돌리는 것이와요. 처음 기여하는 계정의 PR이라면 메인테이너가 승인한 뒤에야 돌기 시작한답니다. 같은 세 명령을 제가 네 브랜치에서 미리 돌려 두었사와요.

| 브랜치 | 코드 변경 | 추가한 테스트 | `pnpm check` | `pnpm build` | `pnpm test` |
|---|---|---|---|---|---|
| `fix/tauri-stream-coalesce` | +10 / −4 | 없음 | 오류 0 | 통과 | 239 통과 |
| `perf/tauri-backup-copy` | +7 / −2 | 없음 | 오류 0 | 통과 | 239 통과 |

| `fix/lowlevelaccess-trigger-copy` | +8 / −8 | 3개, +90줄 | 오류 0 | 통과 | 242 통과 |

본가로 갈 커밋에서는 제 포크용 표식인 `[skip ci]`를 빼 두었사와요. 그러니 본가의 검사도 평소처럼 돈답니다.

## 4. 네 변경이 하는 일

PR 체크리스트의 "Have you understood what the code does?"에 정직하게 답하시려면, 적어도 이만큼은 그대 머릿속에 들어 있어야 한답니다.

### PR 1: 스트리밍 조각 합치기

- **문제:** 데스크톱판에서는 Rust 쪽이 응답 조각을 `streamed_fetch` 이벤트로 넘기고, 웹뷰 쪽 루프가 10 ms마다 큐에서 **딱 하나씩** 꺼내 화면으로 보내는 것이와요. 그래서 초당 100조각을 넘을 수 없고, 조각마다 정규식·CBS·Lua `editDisplay`·sanitize 같은 렌더 과정을 통째로 다시 치르는 것이랍니다. 렌더가 10 ms보다 오래 걸리는 봇이면 큐가 줄지 않고 쌓이기만 하는 것이와요.
- **고친 방법:** 틱마다 그동안 쌓인 조각을 전부 꺼내(`splice(0)`) 하나로 이어 붙여(`Buffer.concat`) 넘기는 것이와요. 바이트와 순서는 그대로이고 조각 경계만 줄어든답니다. 응답 파서들은 원래 경계가 아무 데나 생긴다고 보고 덜 끝난 줄을 모아 두므로 영향이 없사와요.
- **결과:** 서버가 5초에 끝내는 응답이 Windows 무거운 봇에서 23~25초 → 5.4~5.9초, 리눅스에서 126~132초 → 5.8~7.1초가 되었사와요. 둘 다 웹판과 같은 수준이랍니다.

### PR 2: 백업은 Rust 쪽에서 복사

- **문제:** 저장할 때마다 같은 DB를 `database.bin`에 한 번, 새 백업 `dbbackup-*.bin`에 또 한 번, IPC로 두 번 보내는 것이와요.
- **고친 방법:** `database.bin`만 보내고, 백업은 plugin-fs `copyFile`로 디스크에서 복사하는 것이와요. 필요한 권한은 이미 있사와요.
- **결과:** 저장 시간이 절반이 되었사와요 (64 MB 기준 2630 → 1368 ms). 다만 남은 큰 전송 한 번 때문에 최대 메모리는 그대로라, 그 몫은 PR 3이 맡는답니다.

### PR 3: 8 MB씩 나눠 쓰고 이름 바꿔 교체

- **문제 하나:** Windows에서는 IPC 본문 하나가 날아가는 동안 WebView2 브라우저 프로세스가 그 크기의 약 20배, Tauri 호스트가 약 10배를 확보하는 것이와요. 게다가 wry가 그 본문을 창의 UI 스레드에서 읽느라 창이 멈춘답니다.
- **문제 둘:** `database.bin`을 제자리에서 덮어쓰므로, 쓰는 도중에 앱이 꺼지면 잘린 파일이 남는 것이와요. 디코더는 읽지 못한 블록을 조용히 건너뛰어 에러를 내지 않으니, 백업으로 되돌아가는 장치도 움직이지 않는답니다. 캐릭터 10명짜리 세이브를 절반만 남기니 4명만 불러오고 아무 경고도 없었사와요.
- **고친 방법:** `database.bin.tmp`에 8 MB씩 이어 쓰고(첫 조각은 덮어쓰기, 나머지는 `append`), 다 쓰면 `rename`으로 `database.bin`과 바꿔치기하는 것이와요. 다른 프로그램이 파일을 붙잡고 있어 `rename`이 실패하면 `copyFile`로 덮어쓴답니다.
- **결과:** 64 MB 세이브 기준 최대 메모리 2129 → 1089 MB(웹판 1074 MB와 같은 수준), 창 멈춤 합계 0.83초 → 0초, 저장 시간 1368 → 918 ms가 되었사와요.
- **알고 계실 점:**
  - 저장 중에는 `database.bin.tmp`가 잠깐 생기는 것이와요. 불러오기와 백업 목록은 이 파일을 보지 않사와요.
  - 8 MB보다 작은 저장은 IPC 호출이 두 번에서 세 번으로 늘어난답니다.
  - `rename`은 메인 스레드에서 도는 동기 명령이라 저장마다 17~22 ms쯤 걸렸사와요 (한 번은 110 ms).
  - fsync는 넣지 않았사와요. 앱이 죽거나 꺼지는 경우는 막지만, 정전까지 막는 것은 아니랍니다.

### PR 4: lowLevelAccess 값을 원본에 쓰지 않기

- **문제:** 메시지를 하나 그릴 때마다 `runLuaEditTrigger()`가 캐릭터 트리거들의 `lowLevelAccess`를 `false`로 써넣고, 이어서 `runTrigger()`가 캐릭터 설정값으로 다시 써넣는 것이와요. 둘 다 **세이브 속 원본 객체에 직접** 쓰는 것이 문제랍니다. 저수준 접근이 켜진 캐릭터라면 값이 false와 true를 오가고, 저장 감시가 이것을 변경으로 보아 DB 전체를 다시 저장하는 것이와요. 아무것도 바꾸지 않고 스크롤만 8번 했는데 저장이 8번 돌았사와요.
- **고친 방법:** 원본을 고치지 않고 `{...v, lowLevelAccess: …}`로 복사본을 만들어 쓰는 것이와요. 같은 파일의 `runLuaButtonTrigger()`가 이미 이렇게 하고 있었답니다.
- **결과:** 스크롤 8번에 저장 8 → 0번, 16 MB 세이브 기준 IPC 전송 254 MB → 0, 최대 메모리 939 → 491 MB가 되었사와요.
- **알고 계실 점:** 공통 코드라 웹판과 노드 서버판에도 똑같이 적용되는 것이와요. 다만 그 둘은 재지 않았고, 코드를 읽고 내린 추정이랍니다.

## 5. 체크리스트 채우는 법

본가 PR 템플릿의 체크박스는 그대가 정직하게 고르셔야 하는 것이와요. 본 영애의 권고는 이러하답니다.

- **Have you added type definitions?** 새로 정의해야 할 타입이 없고, 새 코드에는 모두 타입이 붙어 있사와요. 체크하셔도 거짓은 아니랍니다.
- **Have you tested your changes? / won't break any existing features?**
  - 테스트와 측정은 제가 그대 대신 리눅스와 Windows 러너에서 했고, 그 사실은 PR 본문 Additional Notes에 이미 밝혀 두었사와요.
  - 그대가 직접 써 보신 뒤에 체크하시는 것이 가장 떳떳하답니다.
  - 그대의 맥에서 확인하려면 맥용 데스크톱 빌드가 필요하와요. 원하시면 그대 포크의 Actions에서 만들어 드리겠사와요.
- **If your PR uses models:** PR 1만 해당한다고 보는 편이 정직하와요. 응답 스트림을 넘기는 방식을 바꾸었으니 각주의 "handling responses from AI models"에 걸리는 것이랍니다.
  - **all models:** OpenAI 호환 스트림만 실측했사와요. 다른 모델(Claude, Gemini 등)로도 응답이 멀쩡히 오는지 보시기 전에는 비워 두시와요.
  - **web, local, and node-hosted:** 고친 곳이 데스크톱 분기뿐이라, 웹과 노드에서는 돌지 않는 코드이와요. 데스크톱은 Windows와 리눅스에서 쟀사와요.
  - PR 2~4는 모델과 무관하니 이 묶음은 비워 두시와요.
- **If your PR is highly AI generated:** 네 PR 모두 80%를 넘으니 체크하셔야 하와요.
  - **understood:** 위 4장을 읽고 납득하셨을 때 체크하시와요.
  - **cleaned up:** 군더더기 없이 꼭 필요한 줄만 고쳤사와요.
  - **not a huge change:** 코드 변경은 가장 큰 PR 3도 35줄 남짓이고, 나머지는 테스트이와요.

## 6. 본가의 AI 판별 봇

본가에는 `.github/workflows/mod.yml`로 [github/ai-moderator](https://github.com/github/ai-moderator)가 걸려 있사와요.

- 이슈를 새로 열 때, 이슈나 PR에 댓글을 달 때, PR 리뷰 댓글을 달 때 돌아가는 것이와요. PR을 여는 것 자체는 대상이 아니랍니다.
- AI가 쓴 글로 보이면 `ai-generated` 라벨을 붙이고, 댓글이라면 접어서 숨기는 것이와요.

이슈 초안은 제가 쓴 글이고, 끝에 AI의 도움을 받았다고 이미 밝혀 두었사와요. 라벨이 붙어도 사실 그대로이니 부끄러울 일이 없답니다. 봇을 속이려고 문장을 비트는 짓은 하지 않았고, 그대에게 권하지도 않겠사와요. 리뷰에 답하는 댓글은 그대의 말로 짧게 쓰시면 접힐 걱정이 덜하답니다.
